The driving indicator, on the guest
===================================
2026-10-14, QEMU guest (Win98 SE, 800x600, Small Fonts, 32MB), gremote
self-updated to stage 4b's build and driven from the host with the gremote
python client over a QMP hostfwd on 7401.

gremote and not the client, because gremote can be driven directly: a step
list goes through the same rc_ui_run the client's agent would use, so the
seam, the strip, both cancel routes and the screenshot bracket are all
exercised without a conversation. What that does NOT cover is named at the
end.

WHAT WAS SEEN
-------------
  indicator-vm-20261014-driving.png       the desktop while a list ran
  indicator-vm-20261014-strip.png         the strip, close up
  indicator-vm-20261014-shot-is-clean.png a SHOT taken while it was up

The strip sits bottom right, above the taskbar, at 442,541-794,566 on an
800x600 screen: "Gaston Remote is controlling the desktop" and a raised
button reading "Stop  Ctrl+Alt+Shift+F11". Nothing is clipped, the text is
the system GUI font, and the whole thing is 352x25.

1. IT APPEARS WHILE A LIST DRIVES, AND NOT OTHERWISE
-----------------------------------------------------
  a 5000ms list    up, 1.5s in                        seen
  a 1000ms list    still up 1.0s after it ENDED       seen (the dwell)
  the same         gone 4.5s after it ended           seen
  a 60ms list      never appeared                     seen

The dwell is what makes back-to-back tool calls read as one drive rather
than a strobe, and the 250ms show delay is what keeps a one-step `focus`
from flashing a topmost window over everything on a P200.

2. BOTH WAYS TO CANCEL IT WORK, AND THEY MEAN THE SAME THING
-------------------------------------------------------------
  Ctrl+Alt+Shift+F11, sent through QMP mid-list:
      the 12s list answered `cancelled` 0.8s later
      the next request was refused `automation_off`
  the Stop button, clicked with a real mouse at 710,553:
      the 12s list answered `cancelled` 0.7s later
      the next request was refused `automation_off`

The second line of each pair is the half that matters. Cancelling the list
is not stopping: the caller's next `run` would start another one within a
second, which is what ROADMAP 4b recorded as the reason this feature exists
at all. In gremote, Stop reaches the tray and turns screen automation off --
that menu item is this program's Stop button, and it is the gesture the user
asked Stop to be the equivalent of.

The button is acted on at WM_LBUTTONDOWN, not BN_CLICKED, because while the
agent is driving the pointer is being teleported between a real button's
down and its up.

3. A SCREENSHOT TAKEN WHILE IT IS UP COMES BACK WITHOUT IT
-----------------------------------------------------------
A `shot` inside the dwell: 481,078 bytes, and the band where the strip sits
is bare desktop. The strip hides, the desktop under it is invalidated and
given SETTLE_MS to repaint, the capture runs, and it comes back.

AND THIS IS WHERE THE RUN FOUND A BUG, which is the point of running it.
The first attempt had the strip IN the picture. The hide was being asked for
and granted -- the log, with a diagnostic added for the question, showed
`mine 442,541-794,566 frame 0,0-800,600` -- so the fault was upstream: the
strip had only just appeared. See 4.

4. THE BUG THE GUEST FOUND: THE FIRST DRIVE NEVER SHOWED THE STRIP
-------------------------------------------------------------------
Before this run, a drive on a freshly started gremote created the window,
registered the hotkey, logged "indicator: up" -- and showed nothing. Four
seconds of driving with nothing on screen.

`driveStarting` starts the indicator's thread and then posts it a wake, and
on the first drive it posts that wake to an HWND that is still null: the
window does not exist yet, because the thread creating it is seconds behind
on a 32MB machine (440ms, measured here). With no wake the clock never
started and the strip never evaluated whether to show.

Fixed by having the thread wake ITSELF once the window exists, which is also
the only moment it can be sure there is one. The second drive always worked,
which is exactly the shape of bug that ships: every test that ran twice
passed.

5. THE CLIENT'S HALF, RUN THE LONG WAY ROUND
---------------------------------------------
gaston raises the same strip through the same seam, but its Stop is its own:
a post of WM_RC_INTERRUPT to the main window, handled on the window thread,
pressing the Stop button the person actually meant. That had been read and
not run, so it was run.

The build was installed as C:\GASTON\G4B.EXE and started, "Let it use this
screen" was found UNTICKED on the Configure menu -- stage 4's item, telling
the truth -- and turning it on reconnected and brought the five screen tools
back into the session. Haiku was then asked for one `input` call with a
9000ms wait, which raised the permission bar ("Use your machine's keyboard
and mouse: pause 9000 ms"); Allow was clicked, and:

  indicator-vm-20261014-client.png     the client's strip, over its window

The strip says "Gaston is controlling the desktop" and offers
"Stop  Ctrl+Alt+Shift+F12" -- different words and a different chord from
gremote's, which is what keeps two of them apart when both programs run.

Then the chord, and the client's log says exactly what was wanted:

    23:15:42.590 indicator: up, cancel with Stop  Ctrl+Alt+Shift+F12
    23:15:56.260 indicator: Stop pressed at the keyboard
    23:15:56.320 stop requested

60 milliseconds from the indicator's own thread to `ComposeBox::doStop`,
which is the Stop button's own log line and the INTERRUPT frame going out.
That is the whole client-only path, on real hardware.

WHAT THE RUN COULD NOT SEE, AND WHY
------------------------------------
The agent did not report `cancelled`; it reported that the machine had
disconnected. That is BACKLOG 38, reproducing underneath the test: the
client's log shows `sync: scan s11646 -> no_root` then `s11647` a second
later, and the bridge's shows a complete HELLO-and-attach once per second
for the whole run. The bridge's own view at 23:15:56 is `ui frame UIEND for
u1, which nobody awaits` -- the guest's cancelled reply arriving after the
connection it belonged to had already been torn down and replaced.

So what the BRIDGE does with that INTERRUPT could not be observed here, and
is covered instead by test_stop_stops_a_running_step_list_and_the_one_behind_it,
which was verified by removing each half and watching it fail. 38 was
already running before this test started and is the user's open item; it was
not caused by anything in this stage.

6. A PARAGRAPH TYPED UNDER IT ARRIVES WHOLE
-------------------------------------------
The keyboard invariant, end to end rather than by inference. Notepad
maximised so its Edit covered 0,38-800,572 -- the strip's own rectangle
among it -- then one list: focus Notepad, type 125 characters. The strip was
up over the text area for the whole of it (indicator-vm-20261014-typing-under-it.png),
and the Edit read back character for character.

That is what `SW_SHOWNOACTIVATE` plus no child control buys. Had the strip
been able to take the foreground, `keyboardTargetOk` would have failed the
step `refused_self` and nothing would have been typed at all.

7. A FULL-SCREEN DOS SESSION HIDES IT COMPLETELY
-------------------------------------------------
Alt+Enter on an MS-DOS Prompt, then a drive. The screendump comes back
720x400 in text mode showing only the DOS session; gremote's log says
`indicator: up`, and the step list answers `ok`. So the drive runs, the
strip exists, and the person sees nothing.

Known and not fixable from here: on 9x a full-screen DOS session owns the
display, and no GUI window is above it. It is the one state where the most
destructive driving happens with no indication at all. Recorded in
ROADMAP's 4b section and BACKLOG 19.

8. TWO STRIPS AT ONCE -- AND THE RUN CHANGED THE CODE
------------------------------------------------------
Both programs driving at the same time (the client on a 25s `input` call,
gremote on a 6s list underneath it). Measured, from gremote's own tree,
which excludes gremote's pid and therefore sees only the OTHER one:

    client strip   GastonDriveIndicator "Gaston"  482,541-794,566
    gremote strip                                 442,541-794,566

The same corner, the same row, the same right edge. The wider of the two
covered the other completely, so the screen said ONE program was driving
while two were -- the strip failing at the one thing it exists for. A person
pressing the Stop they could see would have stopped the other one.

Fixed in the same session: `place()` now looks for a visible window of its
own class and stacks a row above it. Re-run with both driving, both are
readable, each with its own chord
(indicator-vm-20261014-two-strips.png).

That the two can see each other at all is the same fact `BACKLOG.md:2488`
records: `excludePid` excludes only our own pid, so each program's walk --
and each program's occlusion check -- treats the other's strip as an
ordinary window it cannot hide.

9. 640x480
-----------
The strip at the smallest screen this project targets: bottom right, above
the taskbar, nothing clipped, 352 of 640 pixels wide
(indicator-vm-20261014-640x480.png). Changed through Display Properties and
changed back; the guest is at 800x600 as it was found.

WHAT THIS RUN DOES NOT COVER
-----------------------------
- LARGE FONTS (120 dpi). It is the one item of the plan's verification not
  run, because the font size needs a restart on 9x and stage 4's own Large
  Fonts run recorded what that costs on this VM: a wedge at "Windows is now
  restarting", a destroy, and a boot into Safe mode. Not worth doing
  unasked at the end of a session.

  What bounds the risk meanwhile: the width is MEASURED with
  `GetTextExtentPoint32A` rather than laid out, it is clamped to the work
  area (`if (w > work.right - work.left - EDGE * 2)`), and the text draws
  with `DT_END_ELLIPSIS`, so the failure mode is a shortened sentence rather
  than a clipped window. 352px at 96 dpi is about 440 at 120, which still
  fits the 640 screen measured above with 200 to spare. That is an argument,
  not a measurement, and it is written here as one.
