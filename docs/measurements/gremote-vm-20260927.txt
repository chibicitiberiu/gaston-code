=== 5. the reserved out-queue slot ===

A 233,984-byte GET streaming while a second thread pings:
    0.21s, 2 PINGs answered, 0 lost.

Without RC_OUTQ_RESERVE the DATA frames share one flat 64KB budget with the
reply the reader owes, and the server can starve its own heartbeat with its
own answer. This is the case that motivated the libwire change.

=== 6. A RUNNING EXE IS LOCKED -- the thing Wine could not prove ===

This is the measurement worth the whole session, because it went the other
way under Wine.

    a copy of NOTEPAD.EXE, launched:  in the process listing as fffdaf51
    a plain PUT over its image:       REFUSED with `locked`
    still running afterwards:         yes, untouched

    the same write through ship():    killed fffdaf51, wrote 28,672 bytes,
                                      0.19s, nothing left running,
                                      no working files

So ship()'s kill-then-write is not defensive coding, it is the only way the
write happens at all on this platform. Under Wine the plain PUT succeeds --
Wine does not hold the image -- which is exactly the class of thing
`make wine-smoke` is documented as unable to settle.

Noted while finding this: a second GREMOTE.EXE launched under another name
exited immediately and never appeared in the listing, because gremote is
single-instance on a named mutex. The check works. Wine allows the second
instance, so a test written against Wine alone would not have shown it.

The numbers do not move BETWEEN repeats, which is the property the design is

=== 8. REBOOT, and what it does NOT do on this guest ===

REBOOT with no confirm=yes      refused `unconfirmed`
REBOOT mode=sideways            refused `bad_mode`
REBOOT confirm=yes mode=poweroff  acknowledged; Windows began shutting down

What happened next is worth writing down, because two of the three effects
were mine and one was not.

  1. Explorer closed and the taskbar went, but the MS-DOS Prompt stayed and
     the shutdown STOPPED THERE. ExitWindowsEx without EWX_FORCE asks
     applications to close, and a DOS session does not. `force` is a
     parameter of requestReboot for exactly this, and gremote does not pass
     it -- deliberately, since forcing ends unsaved work without asking. On
     a box with a console open, REBOOT needs force or a person.
  2. Closing the prompt by hand let it continue to a bare desktop, and it
     then sat there. This guest has no APM, so EWX_POWEROFF has nothing to
     power the machine off WITH: it gets as far as "everything is closed"
     and stays. `virsh destroy` finished the job. On this VM the useful mode
     is `reboot`; poweroff is for hardware that can do it.
  3. gremote itself exited cleanly on the way down -- its hidden window took
     WM_ENDSESSION and stopped the services, which is what that window is
     for.

One measurement mistake of my own, recorded because it would mislead the
next person: after the shutdown began, connecting to 127.0.0.1:7401 still
SUCCEEDED, and I read that as "gremote has not seen WM_ENDSESSION". It had.
The host-side listener belongs to QEMU's hostfwd and exists whether or not
anything in the guest is listening -- the connection is accepted and then
reset. With a port forward, "the port answers" is not "the server is up".

Noted but not changed: requestReboot runs on the reader thread and
ExitWindowsEx does not return, so Connection::join times out and release()
leaks the socket rather than closing it under a live thread. That is the
correct behaviour of the leak rule, in a process that is ending anyway, and
the alternative -- bouncing the call to another thread -- would add a thread
and a message for no observable gain. If ExitWindowsEx ever fails, it
returns and the reader carries on, which is the case that matters.

=== 9. AUTOSTART -- reachable before anyone logs in ===

The point of the whole exercise, on a box in another room. RunServices runs
before logon; RegisterServiceProcess (resolved, never imported -- it is
9x-only) keeps the process alive across a logoff.

Installed with `REGEDIT /S C:\GASTON\GREMOTE.REG`, then a full stop and
start of the domain, then polled from Linux with NOBODY logging in:

    ANSWERED after 2s
    HELLO os : Windows 4.10 build 2222 A
    free     : 14280 KB of 32288 KB
    processes: 5, EXPLORER running: False
      ffcf6d89 C:\WINDOWS\SYSTEM\KERNEL32.DLL
      ffffba11 C:\WINDOWS\SYSTEM\MSGSRV32.EXE
      ffffaca1 C:\WINDOWS\SYSTEM\MPREXE.EXE
      fffe04c1 C:\WINDOWS\SYSTEM\MSTASK.EXE
      fffe395d C:\GASTON\GREMOTE.EXE
    exec     : Windows 98 [Version 4.10.2222]

EXPLORER absent is the proof that matters: the shell had not started, so
this is genuinely pre-logon and not a desktop with the wallpaper showing. Its
own log agrees -- "registered as a service process; it will outlive a
logoff" -- and it had bound the port within one second of starting, so
TCP/IP is already up when RunServices runs and the 240s bind retry never
came into it.

14280 KB free against 6292 KB with the desktop up: a machine with no shell on
it is a much better place to measure from, which is worth knowing for the
P200's memory numbers.

The key was REMOVED afterwards. A VM that quietly listens on every boot is
not a state to leave somebody's machine in; SETUP.BAT prints the one command
that turns it on and says why it is not automatic.

=== 10. A CD SWAPPED UNDER A RUNNING GUEST GIVES THE RIGHT SIZE AND THE
        WRONG BYTES ===

Cost about twenty minutes, and it is a sharper version of the trap
vmship.sh's comment already describes.

The guest had an older tools.iso mounted. vmship.sh ejected and inserted the
new one, and `DIR D:` immediately showed the new sizes and timestamps -- so
the directory was fresh. But a `COPY D:\GREMOTE.INI C:\GASTON\gremote.ini`
made across that swap produced a file of exactly 136 bytes, the right size,
containing binary garbage. Win98 had cached data blocks from the old disc
while reading directory entries from the new one.

Nothing complained. The symptom arrived later and pointed somewhere else
entirely:

    config: C:\GASTON\gremote.ini: [server] port: not a whole number

...which is the same sentence the client's long-name trap produces, about the
one setting that was not wrong. Re-copying after the swap fixed it.
`COPY D:\FILE.EXE C:\DIR` also silently kept the OLD file; naming the
destination file explicitly (`C:\DIR\FILE.EXE`) worked. **After a media
change, re-copy everything and check a file's CONTENTS, not its size.**

  desktop with NOTHING open -- no DOS box anywhere near it -- so the cause is
