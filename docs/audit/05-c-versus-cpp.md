Fixed: STATIC CONSTRUCTORS DO RUN UNDER nt_win, before WinMain and therefore before rc_log_open -- which reproduces exactly the undebuggable position ("no log file was created") that the whole logging discipline exists to avoid. The audit asked for a grep in make check. Acted on: win/core/rc_cpp.h states the rule with its reason, and `make -C win check` now greps the symbol table for __CPP_INIT/__sti__/_STI__ and FAILS the build if one appears. Currently reports "ok: none".
#
Fixed: new/delete -- OW's default new reaches the CRT's malloc, which is already linked via -bm and _beginthreadex so nothing new arrives, but a second arena is a second fragmentation profile on a machine where memory is the binding constraint. Acted on: operator new/new[]/delete/delete[] are defined in rc_cpp.h over GetProcessHeap(), and with -xd a null return makes Watcom SKIP the constructor, so the existing `if (!p) return;` idiom carries over verbatim from the C.
#
Fixed: DIALECT -- C++98/03 as Open Watcom implements it: no nullptr, no move semantics, no unique_ptr. Acted on: rc_cpp.h is written to that dialect and says so; the guards use private copy constructors rather than deleted ones, and Buf<N> is a plain template with no library dependency.
#
Fixed: MAP SYMBOLS STAY UNMANGLED with extern "C" headers, so the crash-address workflow that tools/stackframes.py depends on is unchanged. Acted on: Step 0 wrapped every header, and make check's stack-frame gate still resolves symbol names after the sync.cpp conversion.
#
Fixed: WHERE THE AUDIT DISAGREED WITH ITS BRIEF -- htmlview.c should be LAST and a rewrite rather than a migration: it has one commit and zero bug fixes in its history and is the only file with real errors, while the bugs live in main.c (19 commits), net.c (12) and sync.c (7), all of which compile as C++ today for free. Accepted: sync.c was the probe, and htmlview.c is deferred by decision rather than scheduled. Its OTHER problem -- that it was an API rather than a view, with nine call sites owning their own markup and scroll policy -- was fixed separately and without changing language (finding 01.2).
#
Fixed: WHAT MUST NOT CHANGE -- the guest transforms nothing, no NT-only APIs, bounded and small allocations, make check staying green. Acted on and verified after every step: the import table is byte-compared against the C build, the four PE gates run on the real binary rather than a spike, and rc_html_block is the single path that accepts finished markup precisely so the "guest transforms nothing" rule stays visible in the code.

# ## The migration plan, and where it stands
#
Fixed: STEP 0 -- extern "C" on all eleven win/*.h inside their existing guards. No language change; the tree still builds entirely with wcc386. Done: verified byte-identical, 285,904 committed at load before and after.
#
Fixed: STEP 1 -- win/core/rc_cpp.h and the build rule. Done: the prelude carries operator new/delete over GetProcessHeap(), Buf<N> with typedef Buf<MAX_PATH> Path, ScopedLock, Handle, FindHandle and HeapPtr<T> with release(); all C++98, all non-copyable where double release would be worse than a leak. The Makefile gained WPP, CXXONLY = -xd and a $(BUILD)/%.o: %.cpp rule. Landed with cppcheck.exe, which exercises each guard and is run by tests/python/test_guest_cpp.py -- 17/17 properties pass under Wine, including destructor ordering on the early-return path.
#
Fixed: STEP 2 -- sync.c -> sync.cpp, the probe. Done as a rename with no code changes, which is what makes the measurement meaningful: identical imports, all gates green, and test_guest_agreement.py still diffing synccheck --limits against bridge/caps.py and agreeing. The second half of this step -- routing join()/rc_sync_begin_write/rc_sync_commit through Path and converting the HeapFree paths to HeapPtr -- is deliberately NOT done here: the equivalent safety already landed in C via rc_strf and a join() that returns its verdict, so redoing it in C++ would be churn without a bug behind it.
#
# The remaining steps are sequenced but not yet taken, and are tracked as
# outstanding work rather than marked Fixed:.

Fixed: STEP 3 -- syncrpc.cpp then net.cpp. Done: syncrpc was a pure rename (its two W836 mixed array/pointer declarations split in passing, output byte-identical). net.cpp is the payoff and it landed as described -- the five statements that freed the rc_frame struct collapsed into one HeapPtr<rc_frame> constructed at the HeapAlloc site, with exactly two release() calls, each at a genuine ownership transfer: RC_ROUTE_TAKEN, where rpc.h says the frame is "consumed AND FREED" so release() prevents a double free rather than a leak, and the successful PostMessage, where net.h gives the frame to the UI thread. The payload frees stayed raw HeapFree because payload is not a frame until rc_frame_parse succeeds. rc_net_send's explicit LeaveCriticalSection count went 5 -> 1; the survivor is the backpressure wait's deliberate temporary unlock, which is NOT a leaked guard -- ScopedLock is a destructor, not a semaphore, and the loop always re-enters before falling through, which is what keeps the guard's own release correct. The BACKLOG §5 n->sock fix was deliberately NOT folded in. Verified after each file from a clean build: import table identical (171 symbols, 7 DLLs, same order) against a fresh build of HEAD in a separate clone, all four gates green with static ctors none, 2122 tests passing and zero skipped, committed-at-load 294,632.
Fixed: STEP 4 -- main.cpp, rpc.cpp, exec.cpp, log.cpp, ini.cpp. Done in two commits as the audit required. rpc/exec/log/ini were pure renames, zero insertions and zero deletions, and needed no RAII guard because none has the repeated free/unlock pattern that earned them in net.cpp. main.c went last and on its own, and it was NOT clean: the W131 'no prototype for ui_send' that every build has carried is a hard error in C++ (E029), because ui_send is static, defined at line 537 and called at 411. A forward declaration fixes it and the build is now warning-free for the first time. Verified on the guest as the audit demanded: shipped, 52/52 probe checks passed on the real machine, import symbol set identical at 171 across 7 DLLs (KERNEL32 and USER32 swap position in the import directory, which is link order, not a semantic change), all four gates green, 2122 tests passing. Committed-at-load fell to 298,784. The BACKLOG §2 memory measurement could not be compared against the 2,312 / 960 KB marks, and why is recorded in PROGRESS: dwAvailPhys now reads 0K on that machine while the app runs correctly, so it is not an availability signal at all.
Fixed: STEP 5 -- frameproto.cpp. Done: exactly the two memchr casts the audit predicted, both in rc_frame_parse, nothing else touched. The binary came out byte-identical at the same file size, which is the strongest form the measurement could take -- a rename plus two casts that change no code generation at all.
Fixed: STEP 6 -- htmlview.c. Closed as a DEFERRAL, not as work done, and this line is the record of that decision rather than a claim to have made the change. It stays C, and it stays out of the migration, because the only thing that would justify touching the COM layer is the COM layer needing to change for its own reasons -- a rewrite carries risk that a rename does not, and there is no bug behind it. The view vocabulary the whole audit wanted (rc_html_notice/error/user/block, owning markup and scroll policy) already landed in C, so the design goal is met without the language change. Reopen when Phase 6 needs the COM layer to change anyway; tracked in BACKLOG.
