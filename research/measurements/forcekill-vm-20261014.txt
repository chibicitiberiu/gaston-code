WHAT WENT WRONG ON THE WAY, BECAUSE IT IS THE USEFUL PART

  1. RUN FROM A DOS PROMPT, THE CASES CANNOT WORK. Started from an MS-DOS
     Prompt this program's own parent is a WINOA386.MOD, and a console it
     opens REUSES that VM instead of making one -- so nothing appears as a
     child and the cases saw vm=0. `--detached-to FILE` exists precisely
     for this and its comment has said so since it was written: "a console
     parent's DOS children share its console ... The client is a GUI
     process; detached is the same." It was simply not the mode being used.

     `inside_a_dos_vm()` now detects it and both cases print
     "VACUOUS (run from a DOS box)" rather than a pass.

  2. AND THE SIBLING CASE HAD BEEN VACUOUS ON THE GUEST SINCE IT WAS
     WRITTEN, for the same reason, reporting `pass` with vm=0. A check
     named for a DOS session had never seen one. Both say VACUOUS now when
     they find no VM.

  3. COMMAND.COM IS THE WRONG TARGET. Trying to force the VM into
     existence, the cases were switched to launching COMSPEC. That is a
     16-bit DOS program, so `kill` denies it without force by an entirely
     different rule, and -- measured -- the pid `Processes::launch` returns
     for one is not usable: the kill came back DENIED because the pid was
     our own. BACKLOG 17 is about a WIN32 CONSOLE program whose console is
     a VM, which is what `--tick` already was.

  4. THE PROCESS TABLE SETTLED IT, and nothing dumped parent pids before.
     `--ps` and `--ps-dos` were added for that. From a GUI parent:

       fffeb759 fffffadd C:\GASTON\EXECCHK.EXE          (parent EXPLORER)
       fffda9b9 fffeb759 C:\WINDOWS\SYSTEM\WINOA386.MOD (parent US)

     From a DOS prompt, the VM is instead our PARENT and a launched
     COMMAND.COM adds nothing. One listing, two contexts, whole answer.

  5. THE FLOPPY SERVES STALE BLOCKS when the image changes under a running
     guest, exactly as the CD does -- a copy reported "1 file(s) copied"
     and the guest kept the old binary. Eject and reinsert, as vmship.sh
     says for hdc.

AND A CLAIM OF 17's PROVED BY ACCIDENT
  The run before the reboot had THREE leaked VMs on the box, left by the
  COMMAND.COM experiments above, and five unrelated cases failed with it:
  stop-reaches-the-grandchild (leaked=1), sink-gone-stops-it (30s),
  cancel-mid-run, launch-and-descendants, kill-waits-for-the-end. After a
  reboot, with vms-on-box=0, all thirty pass.

  That is BACKLOG 17's "degrading later runs" demonstrated rather than
  asserted -- and it is the reason the reclaim this stage added is worth
  having.

  It also disposes of a failure recorded earlier tonight as unexplained:
  `stop-reaches-the-grandchild` was not failing on this guest. It fails
  when run from a DOS prompt, and it fails on a box carrying stranded VMs.
  On a clean box, detached, it passes.
