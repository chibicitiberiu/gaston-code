Keyboard layouts: how Windows 98 produces a character that is not on the key
==========================================================================

Machine : QEMU guest retroclaude-win98, Windows 98 SE 4.10.2222 A, 32MB
Date    : 2026-10-02
Driven  : `KEYPROBE.EXE` (win/checks/keyprobe.cpp), shipped and launched over
          gremote, its KEYPROBE.TXT fetched back. It types into its OWN edit
          control after ActivateKeyboardLayout on its own thread, and reads the
          control back with GetWindowText.
Setup   : the guest had only KBDUS.KBD. KBDGR.KBD, KBDFR.KBD and KBDUSX.KBD were
          extracted from the Win98 SE CD (WIN98_*.CAB) and copied into
          C:\WINDOWS\SYSTEM. Nothing was added to the user's layout list; the
          probe loads them with LoadKeyboardLayoutA, which needs only the files.
Why     : the `input` tool types text on whatever layout the TARGET window has,
          and Wine's layouts are the host's. Everything below decided the
          character strategy in win/automation/input.cpp before it was written.

Findings
--------

1. VkKeyScanExA on a LOADED but not active layout answers for that layout.
   German '@' is vk 0x51 (Q) with mods 6 -- Ctrl+Alt is how AltGr is reported
   and sent on 98, and typing it that way produced '@', '{', '}', '|', '\', '~'
   and EURO on both German and French: 20/20 on each.

2. VkKeyScanExA CAN LIE. On US English it answers EURO (0x80) with vk 0x32 and
   mods 2 -- Ctrl+2 -- and ToAsciiEx for that combination returns 0: no
   character. Typed, it produced nothing at all. So a key is only trusted when
   ToAsciiEx says it produces exactly the character wanted; otherwise the
   character goes by Alt+Numpad.

3. Dead keys are detected by ToAsciiEx returning < 0: '^' and '`' on German,
   '^', '~' and '`' on French. Asking LEAVES THE DEAD KEY PENDING in the
   calling thread; a second ToAsciiEx with VK_SPACE flushes it (returns 1 and
   the bare accent). With the flush in place the whole test string typed as one
   run came back exact on both layouts -- no accent combined with the next
   character. Delivery is the dead key, then Space.

4. Alt+Numpad 0nnn (ANSI, the leading 0) delivered all 20 test characters on
   every layout, with NumLock ON and with NumLock OFF -- keybd_event with
   VK_NUMPADn is the keypad key whatever NumLock says. It is the universal
   fallback for a character no key produces (e-acute and e-circumflex on US).

5. Chords: on French AZERTY '1' is vk 0x31 WITH SHIFT. An accelerator for
   Ctrl+1 is registered against VK_1, so a chord's letter or digit is the VK,
   never the character's shift state. ('z' is VK_Z on all three.)

6. US-International (00020409) did not load from the file alone: its id needs
   the registry entry the layout dialog writes. Not pursued; the strategy does
   not depend on any one layout.

7. Nothing stuck: Shift, Ctrl and Alt all up after the run (GetAsyncKeyState).

Test string (code page 1252): a Z @ EURO e-acute ^ e-circumflex { } | \ ~ ` ' "
u-umlaut sharp-s section 1 &
