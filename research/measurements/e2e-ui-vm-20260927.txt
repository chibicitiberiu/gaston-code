# Bridge: bridge.server on 127.0.0.1:7893. Model: see the note at the bottom.

## The target

Notepad's Find dialog, with "work" typed into Find what so that BOTH buttons
were live -- an agent that clicks the only enabled button has not chosen
anything. Dragged to the top of the screen; see "What got in the way".

## What the agent did

  input: "There is a Find dialog on the screen near the top. Read it with the
          ui tool, then use the click tool to press its Cancel button. Do not
          press Find Next. Tell me the selector you clicked."

  01:21:11  permission allow for mcp__machine__ui     (scope=foreground)
  01:21:34  permission allow for mcp__machine__click  (target=Button[text="Cancel"])

The tree it got back, in part, as the client rendered it:

  radiobutton  "&Down"        263,87  53x20   sel=Button[text=...
  pushbutton   "&Find Next"   329,33  75x23   sel=Button[te...
  pushbutton   "Cancel"       329,62  75x23   sel=Button[text=...
  Notepad      "Untitled - Notepad"  4,0  600x411
    text       "unsaved"

Its words: "I found the Find dialog. Clicking its Cancel button now."
Then: "I clicked Button[text=\"Cancel\"] in the Find dialog."

## Result

The Find dialog is gone and Notepad still holds "unsaved work". That rules out
the two wrong answers: Find Next would have searched and LEFT THE DIALOG OPEN,
and anything that closed Notepad would have lost the text. Cancel is the only
button whose effect is the screen that was captured afterwards.

## What got in the way, and why it is worth writing down

The dialog first used was Notepad's "save changes?" prompt, which Windows
centres ON THE SCREEN. The client's own window also covers the centre of an
800x600 screen. clickAt refuses when WindowFromPoint at the target is not the
target (input.cpp), so the moment the client came forward -- which is exactly
what clicking Allow on its permission bar does -- the button underneath became
unclickable, and the agent is told "occluded: bring the window forward first"
with no tool that can bring a window forward. FOCUS is specified in
REMOTE.md:308 and is not implemented.

The refusal is right. The hole is that an agent cannot get out of it. Filed as
BACKLOG 16.

Worked around here by dragging the Find dialog above the client's top edge,
which is not something an agent could have done for itself.

## Note on the model and the permission mode

Setting the client's permission mode to Auto failed on Haiku: the bridge
logged "Cannot set permission mode to auto: auto mode unavailable for this
model" (bridge/agent/session.py set_permission_mode). Switched to Sonnet; the
permission bar still asked for every call, so both approvals above were given
by hand at the bar. The model is therefore incidental to this result -- what
is being tested is ui and click, not the model.

## The same scenario again, after the BACKLOG 16 fix (01:56)

The run above had to be set up around the bug: the dialog was dragged out from
under the client by hand, from the host, because a covered control could not be
clicked. This run reproduces the ORIGINAL failure deliberately and leaves it in
place.

Setup: Notepad with unsaved text, Alt+F4, so Windows puts the save prompt at
the CENTRE of the screen. Then the client is raised over it by clicking its
taskbar button, until the dialog is not visible at all -- the pixel where the
Yes button was reads as the client's face colour. That is the state that
defeated the first attempt, and it is the state a person creates every time
they press Allow.

  01:56:08  permission allow for mcp__machine__ui     (scope=desktop hidden=True)
  01:56:42  permission allow for mcp__machine__click  (target=Button[text="&No"])

The tree found the dialog behind the client:

  dialog       "Notepad"  270,245  266x126   sel=[class="#32770"]
    pushbutton "&Yes"     284,33

The agent: "The dialog asks to save changes; 'No' discards without saving."
The guest: ANSWERED Click -- Clicked Button[text="&No"].

Afterwards Notepad is gone from the taskbar. "No" discards and closes; "Yes"
would have opened a Save As dialog and "Cancel" would have left Notepad
running, so the taskbar alone distinguishes all three.

No window was moved, raised or closed from the host during the turn. The click
raised the dialog itself.

## UIFOCUS on the guest (02:14)

The op, exercised by an agent on RCW.EXE (433,152 bytes, built 02:09).

Setup: Notepad holding the text "behind the client", then the client raised
over it so Notepad is behind.

  input: "The Notepad window is behind this one. Bring it to the front using
          the focus tool. Do not click anything inside it and do not type
          into it."

  02:13:57  permission allow for mcp__machine__ui     (scope=desktop)
  02:14:42  permission allow for mcp__machine__focus  (target=Notepad Edit)

It read the tree first for a selector, then said "I'll bring the Notepad
window forward using its text control as the target" -- which is the op's
contract: you name a CONTROL and the window containing it comes forward, so a
caller never has to find the top-level window separately.

Afterwards Notepad is in front with an active title bar and a depressed
taskbar button, and its text still reads "behind the client" exactly. Nothing
was pressed and nothing was typed, which is the whole point of having this
op rather than reaching for `click`.

Agent: "Notepad is now in front. I didn't click or type anything inside it."
