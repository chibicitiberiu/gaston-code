installed and produced nothing; the fourth produced all 22 calls. Worth
knowing before anybody picks a hook type by reasoning about which sounds

=== [20/21] which text call does each module make? ===

  (this exe)     TextOutA
  MSHTML.DLL     TextOutW ExtTextOutW ExtTextOutA DrawTextW DrawTextA
  COMCTL32.DLL   ExtTextOutW ExtTextOutA DrawTextExA
  USER32.DLL     no text entry point imported by name
  COMDLG32.DLL   DrawTextA ExtTextOutA TextOutA
  SHELL32.DLL    ExtTextOutA
  RICHED32.DLL   TextOutA ExtTextOutA

**This is a finding against D4, not a confirmation.** The probe's own note:
"D4 patches TextOutA and ExtTextOutA. If the module that draws a web page
imports something else, D4 captures nothing from the one target it exists
for." MSHTML -- the one target -- imports **TextOutW, ExtTextOutW, DrawTextW
and DrawTextA** as well, and the first three are not patched. COMCTL32 and
COMDLG32 add `DrawTextExA` and `DrawTextA`.

So a D4 built on today's patch list would read some of a web page and
silently miss the rest, which is worse than reading none. Widen the list to
the W forms and the DrawText family before anybody builds on it. Reading an
import table needs no injection, so this check is free to repeat on any
machine.

The three checks are `health-a-window-takes-the-foreground`,
`health-a-keystroke-changes-the-screen` (typed=0 sent=6, read back 'health')
and `health-a-write-lands`. Run between each probe rather than once at the
end, so that if the machine had stopped answering the previous line would
name which step did it.

**Nothing died.** Explorer stayed up, the client stayed up, gremote stayed
up, and the box did not spin. The September incident did not recur -- which
is not proof it was these steps' fault or not, only that one more run passed
without it.


=== One thing to fix, found while doing this ===

`PROBE.EXE` opens `PROBE.LOG` with a bare `fopen("PROBE.LOG", "a")` --
relative to the CURRENT DIRECTORY. gremote runs a child in a scratch
directory and deletes it afterwards, so **every probe run driven over the
exec lane writes its log into something that is about to vanish**, and
`C:\GREMOTE\PROBE.LOG` still holds an older run taken when the working
directory happened to be right. The output above survived only because exec
captures stdout.

`probe.c` already has `beside_exe()`, added for `CORPUS.TXT`, so the fix is
to use it for the log too. Same bug and same fix as `focusprobe.cpp`'s
earlier today. Not done here, because changing the probe between its battery
and its health check is exactly the kind of thing this file exists to avoid.
