WHAT IT PROVES, AND WHAT IT ARGUES
  It works: the window title, the whole menu bar, "Page 1/1 (Live)", "New
  chat", the block headings and most of the prose come back readable, which
  is what PLAN.md predicted -- Win98 does not antialias UI text, so plain UI
  text is unusually good input.

  AND IT IS THE BEST ARGUMENT FOR THE TOOL BEING THIRD IN THE LADDER, which
  is a thing worth having in evidence rather than in prose. The menu item
  reads "Let ityse this scien". `ui` returns "Let it use this screen",
  exactly, from WM_GETTEXT, for a fraction of the tokens. A model that
  reaches for `ocr` where a control exists has paid more to get less, and
  the tool's own description leads with that.

  The failures cluster exactly where you would expect and where it does not
  matter much: proportional text at small sizes, the path strings inside
  the tool-call card (c:\vORK\MMPILE.1xt), and the taskbar. The fixed-pitch
  monospace blocks fare worst of all, which is the opposite of the naive
  guess.

THE DEGRADE PATH, WITH TESSERACT GENUINELY ABSENT
  Not monkeypatched: the same 481,078-byte guest capture, fed to the real
  `to_text` in a process whose PATH contains no tesseract at all.

    which(tesseract) = None
    WARNING bridge.uiview: no tesseract on this bridge; a capture cannot
                           be read
    to_text returned: None      (and raised nothing)

  And what the model is told, rendered from the real prompt:

    "This bridge has no OCR engine installed, so the picture cannot be read
     here. The machine captured it (800x600, 481078 bytes) -- that part
     worked. Use `ui` to read the controls, or `shot` to look at the
     picture yourself."

  So a bridge without the engine says so once, names what the machine did
  manage, points at the two rungs that work, and does not fail the tool --
  the contract `to_png` set for a missing Pillow, kept.

THE SAME PATH, REACHED BY ACCIDENT
  The first attempt fed an RLE8-compressed BMP (ImageMagick's default for a
  palette BMP) and leptonica refused it: "cannot read compressed BMP files".
  to_text logged the refusal and returned None, the tool answered with the
  no_engine sentence, and nothing raised -- which is the contract to_png
  established for a missing Pillow, working on a path nobody designed it for.
  The guest never sends a compressed BMP, so this is not a gap; it is the
  failure mode being exercised for free.
