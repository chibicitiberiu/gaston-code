What the list found
-------------------

TWO bugs, and both were only reachable from a real machine.

1. `scope=pid` answered with the WHOLE DESKTOP.

   A Windows 98 process id is an obfuscated pointer with the high bit set --
   EXPLORER.EXE was 0xffffc769 on this run. Every numeric header goes
   through a signed `[0, 0x7FFFFFFF]` clamp, so that value came out 0, and
   `WalkOptions.pid` of 0 means "no filter". The caller got everything and
   nothing said so.

   It is the SHIPPING CLIENT'S bug as well: bridge/wire/protocol.py sends
   the pid as a decimal string and win/ui/uiengine.cpp is the only thing
   that reads it. `strtoul` with base 0 takes the decimal the bridge sends
   and the hex `PS` reports, so neither side had to change to be fixed.

   After:  EXPLORER.EXE 15 nodes, NOTEPAD.EXE 2, out of a 106-node desktop.

2. SHOT answered `failed` with an empty out queue.

   Recorded in ui-lane-vm-20261003.txt: every bulk frame gremote sends
   reserves 8KB for the control lane, so a 63,488-byte body cannot fit a
   65,536-byte queue beside it however long you drain. `UiLink::bodyCap()`
   is per-caller now.

And one thing that is not a bug and reads like one: a step list against a
desktop with TWO Notepads open is `ambiguous`, every time. That is the
engine refusing to pick, which is what it is for -- the fixture was wrong,
not the answer.
