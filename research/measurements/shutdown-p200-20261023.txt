# S1: the self-asked reboot, on the machine the fix was written for.
# It did not happen, and the box is now holding a session that is gone.
#
# Machine : Pentium 200 MMX, Windows 98 SE 4.10.2222 A, 32,284 KB, at
#           10.0.0.158. Same box and evening as deflate-p200-20261023.txt,
#           wire-p200-20261023.txt and ui-cancel-p200-20261023.txt.
#           A real install with RealPlayer, a TV tuner, PowerMenu and the
#           rest resident -- which matters for a shutdown more than for
#           anything else here, because any one of them can veto one.
# Driven  : gremote on port 7401, client closed first so a hang has one
#           suspect (docs/stage5-plan.md's S1).
# Date    : 2026-10-23


=== What was asked, and what happened ===

Every log was pulled off the box first -- gremote.log, gremote.prv,
gupdate.log, gupdate.prv, PROBE.LOG, gaston.log, gaston.prv, seven files --
because docs/REMOTE.md records the evidence being destroyed by the recovery
twice before rc_log_open learned to rename. They are in this session's
scratchpad and the relevant ones are quoted below.

  uptime before          6,741 s
  client                 closed first; KILL answered `pending` and the
                         process was gone on the next PS
  r.reboot("reboot")     returned None, no exception
  the box going down     NEVER. Polled every 3 s for 300 s; port 7401
                         answered throughout
  since then             every AUTH refused `busy`, for 140+ s of polling
                         and counting

And Windows itself is entirely well:

  ping                   3/3, 0.56-0.99 ms
  port 139 (NetBIOS)     open
  port 7401              open, listening, refusing

**So this is not the hang this entry was written to look for.** BACKLOG 35
and REMOTE.md are about a machine that wedges on the way down and needs
Ctrl+Alt+Del twice. This machine never started going down. The OS is
healthy, the shell is up, the network stack is answering on two ports.
gremote is the stuck component, and it is stuck in a specific way: it is
listening, it believes a client is live, and gremote is single-session, so
every new caller gets `busy` and a FIN.


=== What that rules in and out ===

REMOTE.md names two lines that appear only when the shutdown DID NOT happen,
and says seeing either on the P200 is a finding:

  gremote: the shell is still gone a minute after the session end, ...
  gremote: three minutes after the session end this machine is still here,
           so nothing is left to drive; exiting so a new copy can be started

**Neither has fired**, and the second one is the tell. It is a three-minute
watch and more than seven minutes have passed, so if the watch had armed,
gremote would have exited and the port would be closed. The port is open.

That points at the session end never having been signalled AT ALL rather
than at it being signalled and then stalling. The watch counts from the
session end; no session end, nothing to count from. Which in turn means the
interesting question is not "why did Windows not reboot" but "did
ExitWindowsEx get called, and what did it return" -- and the log that would
say so cannot be read while the port refuses to authenticate.

A plausible mechanism worth testing rather than asserting: something on this
desktop vetoed WM_QUERYENDSESSION. It is a real install, and a Notepad
"illegal operation" dialog was seen on this box earlier in the evening.
9x will silently abandon a shutdown a running app refuses. That is a guess
and is labelled one.


=== The second defect, which is the one worth fixing ===

Whatever stopped the reboot, **gremote should not be in this state
afterwards.** The REBOOT caller's connection was closed by the host in the
ordinary way when the `with Remote(...)` block exited. The guest did not
notice, because the server thread was in the shutdown path and never
processed the FIN. So the single session slot is pinned by a peer that is
gone, and the box is unreachable from anywhere for as long as that lasts --
with no remote QUIT, deliberately (REMOTE.md), and RunServices running at
BOOT, so nothing short of a reboot puts a new copy up.

A box that cannot be reached and cannot be told to do anything is the exact
failure BACKLOG 35 closed `mode=poweroff` to avoid. This is a different road
to the same place.

What it argues for: the session-end path should either tear the listener's
session down on its way out, or the shutdown watch should arm when REBOOT is
ACCEPTED rather than when a session end is observed -- so that "I asked for a
reboot and nothing happened" is a state the server recovers from by itself
instead of one that needs somebody in the room.


=== Recovery, which is also S3 ===

The box needs a restart from the Start menu by hand. That is not wasted: it
IS docs/stage5-plan.md's S3, the somebody-else-asked shutdown, and what the
PRVs say afterwards is the measurement. Expected per REMOTE.md:1329 -- the
last clause should be `nothing below this line is ours` rather than `this
process stays up to drive the shutdown it asked for`, because the session end
will have been the Start menu's and not gremote's.

S1 and S2 remain unmeasured. S1 cannot be retried until the box is back, and
should be retried, because one failure does not say whether this is
reproducible or a one-off caused by whatever had a dialog open.


=== Added the same evening: the safety net that should have caught this ===

GREMOTE.INI on this box carries `heartbeat_timeout_s=30`, and
`win/remote/server.cpp:66` turns it into
`m_conn.setIdleTimeout(heartbeatS * 1000)`. A peer that stops talking for
thirty seconds is supposed to lose the slot. That is precisely the situation
here -- the peer is gone and has been for over ten minutes -- and the slot is
still held. Confirmed by polling: AUTH refused `busy` continuously from the
moment the reboot was asked for, past the thirty-second mark by a factor of
twenty.

**The net is strung on the thread it is meant to catch.** The idle timeout is
enforced by the connection's reader, and the reader is what is sitting in the
session-end path. So it cannot fire in the one case it exists for: not a peer
that went quiet while the server was healthy, but a server that stopped
reading while the peer went away.

Which makes three things that all failed in the same direction, and they
should be read as one defect rather than three:

  1. the shutdown was asked for and did not happen
  2. the three-minute "nothing is left to drive" watch never armed, because
     it counts from a session end that was never signalled
  3. the thirty-second idle timeout never fired, because the thread that
     enforces it is the blocked one

Every recovery path gremote has for this situation runs on the thread that is
stuck. A fourth path that does not -- the listener refusing to believe in a
session whose socket is closed, checked where the listener already accepts --
is what would have turned a seven-minute outage into a reconnect. Noted here
rather than in BACKLOG because it belongs with 35 and the shutdown work, and
whoever picks that up should see the measurement that argues for it.

=== S1, on a freshly booted box: all six lines, N = 126 ms ===

After the owner restarted the machine by hand, S1 was repeated with nothing
else changed -- client closed, same build, same INI:

  uptime before          236 s
  r.reboot("reboot")     returned None
  the box going down     9 SECONDS
  back and answering     97 s later

and GREMOTE.PRV carries every line docs/REMOTE.md asks for, in order:

  04:27:01.980 control: REBOOT mode=reboot
  04:27:02.150 app: Windows asks whether the session may end (a shutdown or
               restart); yes
  04:27:08.960 app: Windows is ending the session (a shutdown or restart);
               signalling every service and leaving this handler WITHOUT
               joining any of them
  04:27:09.010 app: the session is ending; abandoning server unjoined
  04:27:09.010 app: every service is signalled and abandoned; cleaning up
  04:27:09.070 mem [exiting]: 7064K free of 32284K phys, 803504K free of
               832096K page, load 73%
  04:27:09.070 === gremote exiting ===
  04:27:09.120 app: the session-end handler is returning to Windows after
               126 ms; this process stays up to drive the shutdown it asked
               for

**All of them, with a small N, and the machine reaching the reboot** --
which is exactly what REMOTE.md specifies. And the last clause is the one it
says to read: `this process stays up to drive the shutdown it asked for`,
not `nothing below this line is ours`. **The 2026-10-01 stay-alive fix is
confirmed on the machine it was written for.**

**So the failure above is STATE-DEPENDENT, not a property of REBOOT.** The
section above should be read as "this is what happens when you ask a box in
that state to reboot", not as "the reboot does not work". The correction
matters because the first reading would have sent somebody to rewrite a
shutdown path that is correct.


=== What that state WAS, and it is the evening's best finding ===

The box that refused to reboot had been running 6,741 s and, crucially, had
**three abandoned ui-lane threads on it**. gremote logged, once per cancelled
walk:

  thread: the ui lane did not stop within 5000ms

`Thread::join(5000)` giving up (win/core/thread.cpp) and the walk thread
carrying on -- each one sitting in an unbounded MSAA call into another
process, because win/automation/msaa.cpp has no timeout and callTimeoutMs
reaches only the WM_GETTEXT in win/automation/tree.cpp. See
ui-cancel-p200-20261023.txt.

A live thread wedged in a cross-process call is precisely what stops a 9x
session end completing. The freshly booted box had none and went down in
nine seconds; the box with three took the shutdown request, never signalled
a session end, and then refused every caller because its own recovery paths
all run on the blocked thread.

That is one root cause with four symptoms, and it reframes two BACKLOG
entries from "slow" and "cosmetic" to "this is why the machine would not
reboot":

  26  a cancel that cannot stop a walk
  39  walking hidden windows opens the Start menu, and the enrichment that
      does it is unbounded
  --  the session end that never fired
  --  the session slot pinned against a peer that was gone

It also argues that BACKLOG 39's option (2) -- skip MSAA enrichment on
hidden windows -- is worth more than its entry claims, because the entry
prices it as a correctness-and-latency fix and this says it is also an
availability fix.


=== S2: the reboot fired, and the box came back without gremote ===

Same again with the client running as well:

  both up                GREMOTE.EXE and GASTON.EXE
  r.reboot("reboot")     the box went DOWN after 6 s
  came back              Windows fully up: ping 0.55 ms, port 139 open
  gremote                NOT RUNNING. Port 7401 refused for 9+ minutes

So S2's reboot half passed -- the shutdown path works with the client up --
and S2's MEASUREMENT is unread, because GREMOTE.PRV and GASTON.PRV cannot be
fetched without gremote.

Why gremote did not autostart is unknown and needs the screen. RunServices
runs at boot, before logon, and 139 being open says Windows got all the way
through networking. The one thing different from the S1 boot that preceded
it is that the client was running when the machine went down. No SMB share
is reachable, so the logs cannot be read remotely either.

**S2 and S3 are both unmeasured.** The manual restart that recovered the
wedged box is not a valid S3: that run was the wedged one, so its PRV
measures the wedge rather than a somebody-else-asked shutdown. A clean S3 is
still owed, on a healthy box, and should be taken after S2.
